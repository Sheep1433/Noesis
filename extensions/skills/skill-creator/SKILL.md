# 技能创作

一个技能就是一个目录，核心是里面的 `SKILL.md`：YAML frontmatter 声明名字和触发时机，正文写给模型看的操作指引。你的职责是帮用户把「每次都要重复讲一遍的做法」变成模型能自己触发的技能。

整体是一个循环：想清楚技能做什么 → 写草稿 → 用 2~3 个真实问法试 → 和用户一起看结果改 → 直到够好。用户说「随便来不用测」，就跳过测试直接交付。

## 创建技能

### 先问清楚

如果当前对话里已经演示过这套做法（用户手动做了几遍后说「做成技能」），直接从对话历史里提取：用了哪些步骤、用户纠正过什么、输入输出长什么样。缺的信息再问：

1. 这个技能要让模型会做什么？
2. 用户说什么话时应该触发？（尽量多列几种原话说法）
3. 期望的产出格式是什么？

### 写 SKILL.md

目录结构：

```text
my-skill/
├── SKILL.md          （必需）
└── references/       （可选：按需加载的补充文档）
```

frontmatter 只需要两个字段：

- `name`：小写中划线，1–64 字符，必须与目录同名。
- `description`：**唯一的触发信号**，要同时写清「做什么」和「什么时候用」。模型普遍倾向于触发不足，所以描述要写得主动一些：不要写「构建内部数据的仪表盘」，要写「构建内部数据仪表盘。凡是用户提到仪表盘、数据可视化、内部指标，即使没明说『仪表盘』也要触发」。

正文写法：

- 用祈使句直接给指令（「先读文件再改」），规则不明显时补一句为什么。
- 例子胜过规则。产出有固定格式的，直接给一个字面示例。
- 正文控制在 500 行以内；领域细节多的拆到 `references/`，正文里写明「做 X 前先读 references/y.md」。
- 用中文写正文，`name` 和通用术语保留英文。

### 安装到平台

- 平台预置技能（`/skills/` 下的）只读，不能改；新建技能一律作为**个人技能**。
- 交付物是一个技能目录。把它打包成 ZIP 后，用户在「设置 → 扩展 → Skills → 上传个人技能」安装；也可以放 skills.sh 市场。
- 你在自己的工作区里写好目录（例如 `my-skill/SKILL.md`），打包或告诉用户文件位置，再给出上面这条安装路径。

## 打磨已有技能

用真实问法逐条试，每条检查三件事：

1. **触发了没有**——没触发通常是 description 写得不够主动或缺了用户会用的词。
2. **结果对不对**——产出格式、步骤顺序是否符合用户预期。
3. **过程顺不顺**——如果模型在重复读同一批文件、绕圈子，说明技能过度规定或语义不清，该删该重写，而不是加更多规则。

改进原则：

- 从个别反馈推广到通用：技能要对付的是没见过的输入。顽固问题换个讲法，往往比再叠一条约束有效。
- 保持精瘦：删掉没起作用的条目再观察。
- 解释 why：讲清原因的规则比全大写的 MUST 更被遵守。
- 发现每次试跑都在重复同一段劳动（比如都现写同一个脚本），就把它固化进技能或 `references/`。

## 修改已安装的技能

- 保持原 `name` 和目录名不变（`research-helper` 改完还叫 `research-helper`，不叫 v2）。
- 用户描述的改动优先落在 description 的触发词上；正文改动保持原有的结构层次，不做无关重排。
