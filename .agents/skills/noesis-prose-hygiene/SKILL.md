# Noesis 写作卫生（会话视角残留防治）

定义 prose 卫生的唯一检验、缺陷分类与按位置的必写覆盖底线。**报告制执行：默认只报告发现与建议改写，未经确认不修改目标文件**（误报的代价高于漏报）。

## 唯一检验

对每段可疑文字问一个问题：

> **只能看到当前仓库的读者（没有会话记录、PR 讨论、未提交草稿、聊天历史），能否解析其中每个引用、验证每个主张？**

不能，则改写为以仓库当前状态为视角的陈述，或删除。能，则不算残留——哪怕它听起来在讲历史。

## 缺陷分类（六类）

1. **死引用** — 指向仓库里不存在的东西：方案编号（"方案 B"、"决策 7"）、讨论稿（"见讨论稿 §4"、"如上所述的设计"）、未被跟踪的文件或会话产物。改写：若被引决策有落点（openspec change、决策记录、bug 记录），改为可解析引用（路径或链接）；否则把该引用承载的事实改写为独立成立的陈述。
2. **变更叙述** — 以"过去如何"为视角讲仓库：「原先 X」「之前这里是」「后来改成」「不再像旧版那样」。改写：陈述现在的行为；已修复的回归写成现在时反事实（「没有 X 就会 Y」），不写仓库史。**保留其中的事实性从句**（见命题保真）。
3. **审查编排** — 复述审查过程：「review 中被否决」「按审查意见改的」「上一轮说」。改写：留下结论与理由作为普通事实，删除"谁在什么时候说的"。
4. **辩解性注释** — 向审查者辩护而非向维护者陈述：「这样写是安全的，因为…」「这只是临时方案」（后者同时是对冲）。改写：陈述让代码安全的不变量；代码本身能表达的删掉。
5. **对冲残留** — 无标记的推迟：「暂时这样应该够用」「先这样，后面再看」。改写：要么升级为 `TODO(name):` 带明确动作，要么改写为实际边界（「上限 N，超过即拒绝」），删除对冲语气。
6. **控制流复述** — 注释复述代码已表达的执行顺序（「先检查 A，再调用 B」）。删除；只有代码表达不了的非显然契约才值得写。

## 中文检索示例（保守初版，从仓库实测采样）

```
原先|之前这里是|原来这里|后来改(成)?|不再(使用|需要|支持|决定|作为)|已废弃|被否|被推翻|见讨论稿|上述方案|方案 [A-Z0-9]|review (中|里|时)|如上所述
```

英文对应：`used to|no longer|the old|this cut|rejected in review|as discussed|per our conversation`。

检索探针是发现手段不是定义——逐条命中后必须语义判断（见下「不是残留的情形」）。

## 不是残留的情形（勿误杀）

- **合法否定保证** — 「X 不决定会话身份」「不再扩展 BgTaskPanel」若读作当前规则成立（"X does not …"），是负向契约，改写仅去掉隐含的历史对比（「不决定」优于「不再决定」），属可选润色不是违规。
- **`TODO(name):` / `FIXME` / issue 引用** — 在 HEAD 上可解析，任何位置都合法，不得搬走或删除。
- **抑制理由** — `lint-disable … -- reason`、coverage-ignore 原因、空 catch 的解释，是必写文字；理由错了改理由，永不删。
- **现在时反事实** — 「没有这把锁，migration 会并发执行」——回归钉子，保留。
- **实测边界** — 「（实测：512 层 ≈ 0.15s）」校准常量；"实测"二字是载荷。
- **运行时新旧状态** — 「旧连接先排空，新连接再接入」是生命周期描述，不是变更史。
- **变更记录类文档的叙事** — `docs/engineering/` 的设计复盘、决策记录的备选方案节、`docs/debugging/` 的排查过程，**允许**按时间叙述（它们的内容就是变更故事）；本 skill 只约束「描述当前状态」的表面：架构文档、README、JSDoc、代码注释、参考文档。
- **`docs/NOTES.md`→`docs/decisions/` 之外的日志类文件** — journal、bug 记录按其自身体裁处理。

## 命题保真（删除前必做）

删除或改写一段文字前，枚举其中的事实性从句：行为、条件与时序、必须/永不等模态、否定保证与例外、所有权、副作用、失败模式、后果。**每个相关从句都必须在改写结果中存活**；只允许删除装饰、重复与视角转写。字数下降本身不是改进。

典型情形（仓库实测样本）：注释写「原先与队列实现放在一起，getter 触发 TDZ 使整页 setup 崩溃」——前半句是变更叙述（删），后半句是不变量（保留为「与队列实现同文件时，getter 触发 TDZ 使整页 setup 崩溃」或等义现在时陈述）。

## 按位置的必写覆盖底线

不是单向删减——缺失的契约要补：

- **公共 API / Service 方法 docstring**：调用方可见的返回值区分、抛出/拒绝条件、副作用、所有权（谁负责释放/关闭）、取消时机、持久化语义。
- **内部注释**：非局部结构与复杂局部结构的取向——不变量、竞态顺序、所有权、安全边界、反直觉的失败行为。删控制流复述与代码重述。
- **模块级 docstring**：角色、依赖、职责、非显然的架构选择；架构选择链接到 owning 文档。
- **测试**：只解释非显然的测试设计（为何这个 fixture/断言/平台适配/间接观察是必要的），删走查与清单。
- **docs/engineering/、README**：当前状态口径；边界、数据流、约束（见 `docs/README.md` 文档地图）。
- **prompts 与用户可见字符串**：措辞即行为，走快照或行为验证，不在本 skill 静默改写（转 `product-facing-copy-audit`）。

## 执行流程

1. 确认范围（显式路径或 diff）；无范围则停下索要，不推断全仓库。
2. 跑检索探针 + 通读范围内最密的 prose（模块 docstring、README、架构文档）——探针有盲区，无模式通读是必要补充。
3. 逐条命中做语义判断：分类 → 是否触「不是残留」豁免 → 命题枚举。
4. 输出报告：每条给 文件:行号、分类、建议改写（保留全部事实性从句）、豁免命中的说明。不改文件。
5. 用户确认后按建议改写；改写完对触达表面跑相应检查（docs 触 `verify_md_links.py`，代码注释随 lint）。
