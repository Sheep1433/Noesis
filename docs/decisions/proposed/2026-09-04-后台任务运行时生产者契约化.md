# 决策：后台任务运行时统一为「单运行时 + 任务类型插件」契约

状态：proposed
日期：2026-09-04

## 问题

后台任务运行时承载两类任务：`subagent`（子 Agent 委派——多轮 LLM 执行、子会话持久化、followup 续跑）与 `shell`（后台命令——一次性执行、无落库、不可续跑）。二者对用户承诺同一套生命周期体验（启动即走、实时进度、可停止、部分成果可回收、子 Agent 可追问），因此**生命周期机制应当是同一套**（状态机、并发准入、停止、终态收口、通知发布）；差异只在执行内容与能力面。

本设计确立目标形态：**生命周期机制收敛为单一运行时，任务差异以「任务类型插件」按契约注入**。验收标准：运行时代码中不存在任何 `kind ==` 判断；新增第三种任务类型（远程委派、定时任务等）只新增插件实现，不改运行时。

## 决策

### 1. 分层与依赖方向

```
工具面 / API 面
  AsyncSubagentToolsMiddleware（模型侧——参照 deepagents 0.6.12
    AsyncSubAgentMiddleware 的结构与语义自研：工具命名、AsyncTask 状态、
    Command 写入、类型清单注入与上游同构；远程适配层不迁移，直调运行时。
    增强：前台等待、description/prompt 双字段、check 来源附录）
  SubAgentMiddleware（同步 task 工具——工厂 subagents= 透传既有装配，与异步并存）
  execute 工具 run_in_background 分支（后台命令入口，与子 Agent 共用注册表）
  SubagentFollowup API（用户侧，与模型同入口）
  ShellJobService（后台命令目录/停止）
        │  解析 SubagentRole → 组装 TaskRequest（工具面直调运行时，无 client 层）
────────▼────────────────────────────────────────────
TaskRuntime（运行时，kind 无关）
  身份与注册表 / 状态机 / 两级并发准入 / 三级计时器
  终态单次收口 / 事件与通知发布 / 快照查询
        │  TaskKindRuntime 契约
────────▼────────────────────────────────────────────
SubagentKind                     ShellKind
  worker 编译工厂（角色配方）       backend 命令执行
  子会话持久化（经端口）            无落库 / 不可续跑
  followup 队列与冷恢复
  危险操作工具层拒绝（见 §5 执行）
        │
  隔离事件循环（任务比主 run 活得久的执行落点）
```

依赖单向：工具面 → 运行时 → 契约；插件只依赖契约类型与 entry 类型，不依赖运行时主体。子会话等产品数据经 `SubagentSessionPort` 窄端口写入 service 层——运行时与插件都不直接依赖产品服务。

**运行时是显式的进程级单例实例**——配置与注册表同属实例，替代「实例持配置、模块级全局持注册表」的分裂形态；测试经实例注入与重置缝，不操纵模块全局。

### 2. 数据模型

三个数据结构各司其职，避免「一个对象既是执行状态又是对外投影」的旧病：

```python
TaskRequest    # 一次提交的完整描述（frozen）：kind、description、session/user、
               # role + prompt + child_launch（subagent）| command + backend（shell）

TaskEntry      # 注册表内条目：
               #   task: TaskTicket                —— 对外投影数据
               #   behavior: TaskKindRuntime       —— 该 kind 的行为对象（无状态单例）
               #   payload: Any                    —— kind 私有执行状态，运行时不读不解释
               #   future / watchdog / stop_grace / stop_reconcile 计时器
               #   terminal_published              —— 终态单次收口归属标记
               #   session_max_concurrent / timeout_seconds

TaskTicket     # 对外快照（wire 扁平）：task_id、child_session_id（公开身份优先）、
               # kind、subagent_type、status、result/error/stop_reason、
               # step_count/turn_count、起止时间、progress（有界 deque）、retrieval_sources
```

`TaskTicket` 与 `TaskEntry` 分离的意义：所有查询路径（API、工具、事件）只碰 ticket 的**新鲜构造副本**，注册表活对象永不外泄（dsh JobSnapshot 纪律的同构物——快照即投影，改了不回写真身）。

### 3. 状态机（运行时唯一拥有）

```
queued ──调度──▶ running ──正常结束──▶ completed
  │                │ ├──停止请求──▶ stopping ──静止边界退出──▶ cancelled
  │                │ │                └──宽限超时──▶ 硬杀 → cancelled / timed_out
  │                │ ├──看门狗超时──▶ stopping(timed_out) → timed_out
  │                └──执行异常──▶ failed
  └──取消（未调度）──▶ cancelled

复活：completed / cancelled ──followup──▶ running（仅 supports_followup 的 kind）
```

运行时强制规则（插件不可绕过）：

1. **槽位计量** = `running + stopping`；`stopping` 占槽保证收尾期间不饿死同会话后续任务。
2. **终态互斥**：`completed / failed / cancelled / timed_out` 四值互斥；停止族终态只能经停止路径进入，`failed` 只能来自执行异常。
3. **复活纪律**归运行时：取消旧 future、重置三个计时器与 `terminal_published`、清除停止信号——统一执行，不允许各插件自写善后。**复活资格**：`completed / cancelled`（执行/意图分离——停止只终止执行，续聊意图保留）；`failed / timed_out` 不可复活。实现时同步主规格的 followup requirement（现行规格文本未含 cancelled，属规格滞后于代码）。
4. **迟到事件防御**：终态后到达的执行事件一律丢弃并计数告警。

`stopping` 单独存在的理由：停止运行中的子 Agent 不能一刀切——悬空 tool_calls 会破坏 LangGraph checkpoint 完整性。受理即时（状态立刻转、快照立即可见），执行侧在静止边界（当前步骤完成）退出，30 秒宽限超时硬杀，再兜一层对账强制终态。三级兜底（协作 → 宽限硬杀 → 对账）是停止路径的全部安全网。

### 4. 生产者契约

```python
class StopMode(Enum):
    COOPERATIVE = "cooperative"      # 置停止信号，静止边界退出，宽限超时硬杀
    IMMEDIATE_CANCEL = "immediate"   # 运行时直接 cancel future，即时终态

class TimeoutPlan(Enum):
    COOPERATIVE_TIMED_OUT = "cooperative"   # 转 stopping(timed_out) + 宽限
    HARD_KILL = "hard"                      # 锁外强取消 + 强制终态

@dataclass(frozen=True)
class TaskOutcome:
    """run() 的终局描述；运行时据此收口，不解释字段。"""
    status: Literal["completed", "failed"]
    result / error / finish_reason / usage / model_calls

class RunContext:
    """run() 执行期由运行时提供的服务通道（闭包构造，隔离 loop 安全调用）。
    面克制为四方法，扩张需走决策。"""
    publish_progress(event)                # 过程摘要（有界）+ 任务事件
    record_retrieval_sources(sources)      # 去重合并来源清单
    publish_run_event(event, payload)      # 子会话 run 事件流（经端口）

class TaskKindRuntime(Protocol):
    kind: str
    # —— 能力声明（运行时据此门控公开 API）——
    supports_followup: bool   # False：followup 族在锁内即拒绝（文案由插件提供）
    has_turns: bool           # False：通知负载不携带 turn_count
    # —— 行为注入 ——
    def run(self, ctx, entry) -> Awaitable[TaskOutcome]            # 执行内核
    def request_stop(self, entry) -> StopMode                       # 停止模式选择
    def on_timeout_locked(self, entry) -> TimeoutPlan               # 超时计划选择
    async def deliver_followup(self, entry, message, params) -> Awaitable
                                                                    # 入队或构造新 turn 首输入（含冷恢复的
                                                                    # 新 run 创建，返回前完成——run_id 权威）。
                                                                    # 运行时已在锁内完成校验与状态占位后
                                                                    # 调用，本方法无锁执行
    def build_payload(self, request) -> Any                         # kind 私有状态构造
```

**锁纪律是契约的一部分**（随协议 docstring 交付，review 与契约测试依据）：

| 方法 | 调用上下文 | 实现禁区 |
|---|---|---|
| 能力字段 / `request_stop` / `on_timeout_locked` | 持 `_TASKS_LOCK` | 不得再取锁；不得 I/O / await |
| `run` / `deliver_followup` / `build_payload` | 无锁（隔离 loop 或主 loop） | 不得直接操作注册表与 future；经 ctx 或返回值表达意图 |
| payload 跨线程读写 | `entry.payload_lock` | 主 loop 不得直接 await 隔离 loop 对象 |

插件必须是无状态单例：任务私有状态全部在 payload，行为对象不得持有任务集合（防止第二事实源）。

### 5. 生命周期路径（责任分解）

**提交**：**双入口共用同一注册表**——`start_async_task`（子 Agent，经角色解析分发）与 `execute` 的 `run_in_background` 分支（后台命令，保持单工具形态的既有产品契约）。子 Agent 先经 service 完成 child session launch 事务（任务未跑、卡片已可见）；两个入口提交后都经 `Command` 把任务身份写入 `async_tasks`（压缩免疫的任务清单对两类任务一致）。check / cancel / list 为 kind 无关的运行时查询，两类任务同面可见；`update_async_task` 对命令经 `supports_followup` 能力门拒绝（文案含替代指引）。运行时锁内造 ticket + entry，两级准入；获槽则把 `behavior.run()` 调度到隔离 loop，未获槽入会话 FIFO。**提交路径零重资源**——worker 编译延迟到 `run()` 内（隔离 loop 资源绑定的约束也在此满足：LLM 客户端与 checkpointer 池在使用它们的 loop 上创建）。

**执行**：subagent 插件工厂惰性编译 worker、逐 turn 驱动、过程经 ctx 发布；shell 插件经 backend 执行、流式收集（有界滚动缓冲 + 超限落临时文件）。终局以 `TaskOutcome` 返回，异常即 `failed`。**worker 不交互、不审批**：工具集不含 ask_user（歧义在结果中说明假设后继续），触发审批条件的危险操作（如危险命令）在工具层确定性拒绝并携带结构化拒绝事实——主 Agent `check` 收果时可见，可在主 run（用户在场、审批 UX 自然）中升级执行；后台任务因此永不等待人。

**停止**：`runtime.cancel()` 锁内查 entry → 终态幂等返回 → `queued` 出队即终态 → `running` 问 `request_stop()`：`COOPERATIVE` 置 stopping + 信号 + 武装宽限（乐观终态：快照立即生效，收尾异步补齐）；`IMMEDIATE_CANCEL` 锁外 `future.cancel()`（插件不碰 future）。协作路径在静止边界以 `TaskOutcome(result=部分产出)` 返回，运行时收口；宽限超时 → 硬杀 → 对账兜底。

**超时**：watchdog 到点 → 锁内 `on_timeout_locked()` → 锁外按计划执行（subagent 协作 timed_out；shell 硬杀），其余同停止路径。

**followup**：`runtime.deliver_followup()`（**单一异步入口**，无同步版——见 §11 删除清单）：锁内完成能力门控（`supports_followup`）、复活资格校验与状态占位（`RUNNING`，占位窗口内到达的停止由宽限对账兜底）→ 锁外 `await behavior.deliver_followup()`——运行中任务入队（队列与 turn 参数构造是插件私事），可复活终态在此完成新 run 创建后由运行时调度新 run。分工线：**插件说「下一条消息是什么」，运行时说「怎么安全地再跑起来」**。

**终态收口**：`terminal_published` 首个置位者负责：ticket 终值 → 子会话终态落库（经端口，含 usage/model_calls）→ 任务事件 + run 事件 → 通知入队（preview ≤80 字 + 来源清单）→ `auto_continue` 去抖唤醒（仅 completed，60s 窗口合并多终态）→ 唤醒排队任务。收尾在锁外执行，重入注册表须重新持锁。

### 6. 两级并发准入

```
submit → 全局准入（max_concurrent_global，默认 12）→ 会话准入（max_concurrent_per_session，默认 3）
       → 未过者入该会话 FIFO；终态释放槽位后按序唤醒（全局按提交序，防会话间饿死）
```

排队任务不占槽、不编译；排队状态（`queued`）对 ticket 可见。会话级上限防单会话独占，全局级是进程总闸（新增——此前只有会话级，多会话并发委派时无护栏）。

### 7. 持久化、通知与可观测

- **subagent**：产品数据全经 `SubagentSessionPort` 落标准表；重启后注册表丢失（接受的设计限制），启动对账把遗留活跃子 run 收口为 error（`SUBAGENT_PROCESS_RESTARTED`）。
- **shell**：不落库，重启即丢（接受）。
- **通知**：终态入会话通知队列（内存，与注册表同生命周期）；下一 run 组装输入时 drain 注入（`[系统通知]`，一次性）；run 活跃时由通知中间件在模型调用边界即时注入；`auto_continue` 无活跃 run 时自动创建 continuation run。
- **任务身份**：`start_async_task` 经 `Command` 写入主 Agent `async_tasks`（上游 AsyncTask 结构，checkpoint 持久化、免疫压缩）；state 是投影，权威永远实时查运行时（miss 落 DB）。
- **运行时公开面**（`ExecutorPort` 白名单由此自动派生）：`get` / `list_for_session` / `sources_of`（查询，miss 落 DB 兜底）；`submit`；`cancel` / `deliver_followup`（控制，后者单一异步入口）；`subscribe_run_events` / `unsubscribe_run_events` / `get_run_event_history`（事件，经端口）；`fail_session_tasks` / `shutdown`（生命周期）。
- **对外接口白名单自动派生**：`ExecutorPort` 面从运行时公开方法生成——手工白名单曾漏 `asend_message` 导致全部 followup 500 的事故，以此根治。

### 10. 测试策略

1. **运行时契约测试**（FakeKind 按剧本返回动作，不依赖真实执行；运行时经实例注入，测试间显式重置）：状态机全转移、两级准入与唤醒序、停止三模式、终态单次收口、复活纪律、迟到事件丢弃、快照不可变。
2. **插件集成测试**：SubagentKind 用脚本模型跑全生命周期（含 followup 冷复活、危险操作拒绝路径）；ShellKind 用假 backend。
3. **端口契约**：`ExecutorPort` 面 == 运行时公开面。
4. **端到端**：工具面 → 运行时 → 插件 → 端口 → DB（subagent + shell 各一轮真实链路）。

### 11. 随本设计删除的存量代码

以下形态在新设计中不再存在，实现时直接删除，不保留兼容层：

1. **followup 同步版（`send_message`）与异步版（`asend_message`）的双版本**。只留单一异步 `deliver_followup`。双版本是 run_id 竞态修复时「加新未删旧」的遗留，端口白名单漂移事故（漏 `asend_message`）正是它直接造成的——白名单里躺着旧同步版，新异步版无人记得登记。同理删除 `start_task` 工具的同步回退分支（langgraph 工具实际恒走 coroutine，该分支不可达）。
2. **模块级 `_TASKS` 全局注册表**。状态归运行时实例（见 §1），测试不再直接操纵全局字典。
3. **`create_noesis_agent` 的 `subagents=` / `async_subagents=` 透传参数**。从未被任何装配使用，挂着只会让读者困惑「哪套子 Agent 机制是正主」。
4. **`validate_followup` 作为独立公开方法**。校验折叠进 `deliver_followup` 的锁内前置步骤——独立存在只是历史 API 面的惯性。
5. **`NoesisSubagentMiddleware` 五工具（`tools_middleware.py`）**。由参照上游语义自研的 `AsyncSubagentToolsMiddleware` 取代——Command 写 state、类型清单注入、未知类型拒绝等机制与上游同构，自研工具面整体退役。
6. **子 Agent 的 HITL 审批全套**。后台任务无人值守，等待审批是反模式（最坏情形：任务挂起 24 小时后被超时拒绝）——审批回到用户在场的主 run 中发生（worker 危险操作经工具层确定性拒绝，拒绝事实随结果回流，主 Agent 可升级执行）。随之删除：worker 的 `interrupt_on` 装配、`awaiting_approval` 状态族与审批续跑路径（跨事件循环 `Command(resume)` 摆渡、usage 双种子、投影种子 `turn_seed_content`、审批超时看门狗、stopping 与审批的优先级仲裁）、子会话抽屉的审批卡 UI 与事件。**主 Agent 的 HITL（ask_user 澄清、工具审批）不受影响**——那是用户在场的交互，与本项删除的后台场景无关。

以下两项**形似包袱但为约束所迫**，保留并写明重估触发条件：

- **注册表与通知队列在内存**：受单实例架构（LeaderElector 单进程模式）约束，与 run 调度同生命周期。重估触发：分布式 run 总线落地时，注册表外置随该变更一并设计。
- **shell 停止的立即取消语义**：现行 backend 命令执行无协作边界。改为可协作停止（runner 支持 kill）是行为变更而非重构，超出本设计；若做，ShellKind 的 `request_stop` 返回值从 `IMMEDIATE_CANCEL` 改 `COOPERATIVE` 即可，契约不变。

## 备选方案

- **两类任务各写一个执行器**：状态机、停止、收口各复制一份，每个 bug 修两遍；仅当两类任务的状态词汇真正分叉时重估。
- **进程隔离（每任务一进程，身份即启动旗标）**：隔离最彻底、崩溃不波及，但后台/followup 冷恢复依赖进程内 checkpoint 与子会话持久化，进程模型承载不了；保留为未来远程执行方向——届时新增远程 kind 插件，运行时契约不变。
- **插件只声明能力、不做行为注入**：写起来省事，但每加一种任务类型仍要改运行时，违背验收标准。
- **逐行复制上游中间件（fork ~950 行最小 diff 维护）**：改动自由，但远程适配层（client 体系）对本进程场景是死重，且背上 fork 的长期移植成本；参照自研只借语义（命名 / 状态结构 / Command 机制与上游同构），代码量与维护面回到自己掌控。
- **注入复用（调上游私有 `_build_*_tool` 构建器、注入 client）**：零 fork 代码量，但依赖下划线私有函数，上游任何重构即碎。

## 后果与代价

- 契约的锁纪律无编译期强制，靠协议文档、评审、FakeKind 契约测试三层维护。
- `RunContext` 四方法是契约的全部回话面，每加一个方法都是契约扩张，需走决策。
- 两级准入的全局 FIFO 在单会话长任务占满全局槽时，其他会话可感知排队延迟——需暴露全局排队深度指标。
- `max_concurrent_global` 是新增总闸，默认值（12）上线后按真实负载校准。
- **参照实现的语义漂移风险**：上游演进不自动同步，工具命名与 `AsyncTask` 状态结构有意锁定在 0.6.12 形态；升级 deepagents 时人工对照上游语义变化决定是否跟随。
