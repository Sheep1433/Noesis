# 决策：后台任务子系统物理拆分与边界收口

状态：implemented
日期：2026-09-19

## 问题

后台任务运行时（subagent / shell 双 kind，2026-09-11 起为单一运行时 + kind 插件契约）全部机制挤在 `agents/subagents/executor.py` 单文件（2501 行）：状态机、隔离循环、登记表、排队、事件投递、终态收口、双执行内核、门面。由此产生四个具体病灶：

1. **模块边界名存实亡**：物理拆分到 `jobs/` 后，门面仍重导出约 40 个下划线内部名（注释自认"兼容层"），测试与服务层继续从门面摸注册表内部——改 `jobs/` 内部名会"意外"破坏门面导出，边界感建立不起来。
2. **工具面摆放不对称**：subagent 的工具面在包顶层（`async_tools_middleware.py`），shell 的在子包内（`shell/entry.py`），同一概念两种摆法，读者无法建立稳定预期；两 kind 共用的任务身份 graph state 投影（`async_tasks` 键）藏在 subagent 工具面文件里，shell 侧反向依赖它。
3. **kind 注册表位置倒挂**：协议与 `behavior_of()` 在 `kinds.py`，注册表数据 `KIND_BEHAVIORS` 却在门面底部——`behavior_of` 每次延迟导入门面（循环依赖气味），新增第三种 kind 必须改门面文件。
4. **死代码与残留**：`get_memory` 与 `get` 逐行重复；`pop_followups` 零调用（kernel 直接消费 `entry.followups`）；settle 日志写死 "bg subagent"（shell 任务同路径误标）；`SubagentSessionPort as SubagentSessionService` 别名让一个端口两个名字；定时器族 start/cancel 不对称（reconcile 启动是裸字符串反射）。

另有清理债：`agents/simple_mcp.py`（调试 Agent）删除后 CLI 断链；`agents/runtime/` 死目录（引用已删除的 ToolRegistry）。

## 决策

**分层规则一句话：顶层放跨 kind 共享物，kind 专属物进子包，每个子包都是 kernel + 工具面。**

```
agents/background/
├── jobs/          state（状态机与快照）/ loop（隔离循环）/ registry
│                  （登记表与排队）/ events（SSE 投递）/ settle（终态收口与定时器族）
├── subagent/      kernel.py（turn 链内核）+ roles.py（角色注册表）+ tools.py（5 个异步任务工具）
├── shell/         kernel.py（命令内核）+ tools.py（execute 工具替换器）
├── task_state.py  两 kind 工具面共用的任务身份 graph state 投影
├── kinds.py       TaskKindRuntime 协议 + KIND_BEHAVIORS 注册表
├── executor.py    门面（Executor 类 + shutdown + 运行时端口装配）
└── notifications / notify_middleware
```

配套规则：

- **门面不重导出内部名**。测试与服务层直接从所属模块导入（`_TASKS`/`_TaskEntry` → `jobs.registry`，settle 族 → `jobs.settle`，事件族 → `jobs.events`，`_ensure_loop` → `jobs.loop`）。checkpointer 对可重绑定的 `_loop` 经 `jobs.loop` 模块属性取值；门面的 PEP 562 `__getattr__` 代理随之删除（checkpointer 是其唯一消费者）。
- **`KIND_BEHAVIORS` 收回 `kinds.py`**，类型 `dict[str, TaskKindRuntime]`。因 kinds 与两个内核互相依赖（内核 import `StopMode`），内置 kind 惰性注册：`behavior_of` 首次调用时填充——顶层导入依导入顺序崩坏，自注册 import 副作用则依赖导入时序。新增第三种 kind 只改 `kinds.py`。
- **`__init__` 只导出 10 个稳定契约**（Executor、Task、Status、shutdown、fail_session_shell_tasks、双中间件、角色注册表三件），docstring 写明下划线纪律：`__all__` 之外皆包内实现，跨模块协作与测试可直接引用，但改动不承诺兼容。
- **定时器族 API 对称**：watchdog / stop_grace / reconcile 三族均有 `start_*_timer` / `cancel_*_timer`，消灭裸 `_loop_timer_arm(entry, "stop_reconcile_handle", ...)` 字符串反射。
- **端口调用统一 `SubagentSessionPort` 本名**（settle 1 处 + kernel 4 处），契约测试正则同步。
- **删除清单**：兼容重导出块、`__getattr__`、`get_memory`、`pop_followups`、`PRIVATE_STATE_KEYS`（零消费者死常量）、CLI 的 simple_mcp 模式（`noesis_cli/client.py` 的映射项、枚举项、`isinstance` 分支与 main.py 帮助文案）、`agents/runtime/` 死目录、包级 `registry.py→roles.py` 改名（消除与 `jobs/registry.py` 同名异义）。
- 行为零变化：本轮只动结构与命名，全量测试通过是验收条件之一。

## 备选方案

- **bash 与 subagent 彻底解耦（两套机器）**：被否。二者共享约七成最难写对的并发机器（登记表、状态机、收口契约、看门狗、通知），解耦等于复制；模型工具面、前端任务面板、通知唤醒三处依赖统一契约。采用"概念统一保留、物理彻底分离"——共享机制一个家（jobs/），kind 差异各归子包。
- **保留门面兼容重导出层、测试逐步迁移**：被否。兼容层没有拆除日期，且让"哪些名字是稳定契约"永远无法从名字判断；一次性迁移约 30 处测试导入是纯机械操作，成本一次付清。
- **kind 注册表独立 `kinds_registry.py` 模块或内核自注册（import 副作用）**：被否。前者多一个文件只放一个 dict；后者依赖导入时序（先 import 内核再调 `behavior_of` 才有注册表），测试注入 fake kind 时序更脆。惰性注册把时序问题变成确定性初始化。
- **`_TaskEntry` 按 kind 拆子对象（entry.subagent / entry.shell）**：暂缓。属行为邻近的结构变更，与"每任务独立循环"（Phase 4b）同批独立验证，不在本轮零变化承诺内。

## 代价

- 测试与服务的导入路径一次性迁移约 35 处（6 个测试文件 + 5 个服务/配置文件）；此后读测试需要知道内部名的所属模块（由 `__init__` docstring 与各模块 docstring 承载）。
- `kinds.py` 的惰性注册是"首次调用初始化"模式，读代码时注册表填充点不在模块顶层——以注释与 `behavior_of` 的单一路径弥补。
- `_TaskEntry` 仍是 25 字段胖条目（kind 专属字段混居），跨 kind 字段交错读起来费劲——已记录为目标态规划项（设计文档 §8.5 Phase 4b 邻近）。
