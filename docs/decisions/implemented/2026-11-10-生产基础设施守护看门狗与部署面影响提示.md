# 决策：生产基础设施守护——看门狗 + 部署磁盘硬阈值 + 影响面工具认识部署面

状态：implemented
日期：2026-11-10

## 问题

两次生产事故的共同根因是"信号存在但无人消费"：磁盘满前零告警（Postgres
进入崩溃循环、登录 502）；advisory lock 断连后容器连续 unhealthy 五天
（15089 次 healthcheck 失败）无人知晓——`/health` 忠实返回 503，只是没有
人看。另有部署面耦合事故：worker-role-split 改代码漏改部署面，nginx
upstream 指向已删的 `backend` 服务名，线上 502 中断 35 分钟。

## 决策

1. **看门狗**（`deploy/watchdog/noesis-watchdog.sh`，部署于服务器
   `/root/zzq/` + crontab 每 5 分钟，位于仓库 checkout 之外不受
   git reset/clean 影响）：单脚本双探测——磁盘水位（≥85% 或 <10G）与
   `https://zzqnoesis.cn/health`（一个端点覆盖三类故障：502=后端停、
   503=锁丢失降级、超时=宕机）。状态跃迁即告警、持续异常每小时重报、
   恢复发通知；探测结果落 `/var/tmp/noesis-watchdog.state`。
2. **告警通道**：复用 Noesis 用户 Telegram 通道的 bot（经容器内解密
   `channels.json` 的 `enc:` Fernet 密文**一次性导出**到
   `/root/zzq/.watchdog.conf`，600 权限，仅 bot_token/chat_id 两行）。
   看门狗读该文件直连 `api.telegram.org`——与 Noesis 进程完全解耦，
   Noesis 停机时告警照发；bot 轮换时重新执行导出即可（见下）。
3. **部署磁盘硬阈值**：`deploy-remote.sh` 清理步骤后校验剩余 <10G 即
   `die` 拒绝部署——build 中途耗尽磁盘会把栈留在半部署态，且满盘会让
   Postgres 进崩溃循环。
4. **`change-scope.py` 跨层耦合提示**：diff 触及后端启动形态
   （web/control/worker/app/bootstrap）→ 提示核对 compose 服务、nginx
   upstream、部署脚本服务引用；触及 compose → 提示同步 nginx 与停服
   名单；触及配置样例 → 提示同步服务器实文件。文本与 `--json` 输出
   均携带。

告警密钥导出命令（bot 轮换时重跑）：

```bash
docker exec noesis-web-1 python3 -c "
import glob, json, sys
sys.path.insert(0, '/app')
from noesis.config.secrets import SecretCipher
from noesis.services.messaging_channel_service import _runtime_token
for p in glob.glob('/data/noesis/users/*/channels.json'):
    d = json.load(open(p))
    for c in d.get('channels', []):
        if c.get('type') == 'telegram' and c.get('enabled'):
            print('BOT_TOKEN=' + _runtime_token(str((c.get('secrets') or {}).get('bot_token') or '')))
            print('CHAT_ID=' + str((c.get('pairing') or {}).get('chat_id') or ''))
            raise SystemExit
" > /root/zzq/.watchdog.conf && chmod 600 /root/zzq/.watchdog.conf
```

## 备选方案

- **`monitor_advisory_lock` 内部加外发告警**：被否——容器进程内的告警在
  进程僵死时同样哑火，且给核心代码加出站 HTTP 依赖；`/health` 探测从
  外部覆盖同一信号，一条路径管两类故障。
- **UptimeRobot 等外部拨测服务**：更稳（服务器整机宕机也能告警），但
  需要注册账号，先以自建看门狗覆盖（服务器整机宕机时用户访问也会立刻
  发现）；需要时再叠加，与看门狗不冲突。
- **看门狗运行时经 `docker exec` 解密取 token**：被否——告警依赖容器
  存活，"后端停"恰恰是最需要告警的时刻（循环依赖）。
- **构建缓存定期 cron 清理**：被否——`deploy-remote.sh` 每次部署已
  prune，看门狗水位告警兜底增长（11-01 部署后缓存涨到 5.9G、水位
  90% 时告警实测触发并人工清理回 80%）；再加定期清理会掩盖增长趋势。

## 代价

- bot token 在服务器上有一份明文副本（root-only 600）：泄漏面从
  "channels.json 密文 + 加密密钥"扩大到 "+一个 root 文件"；换来的是
  告警与被守护系统解耦。bot 权限仅限该 bot 的会话，风险可接受。
- 看门狗脚本有仓库版本（`deploy/watchdog/`）与服务器部署副本两份，
  改仓库版后需手动同步到 `/root/zzq/`（部署副本是权威运行物）。
- `change-scope.py` 的提示是路径模式触发（不解析 compose 内容语义），
  覆盖常见耦合而非全部。
