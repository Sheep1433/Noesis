# 决策：子代理停止改乐观终态（删除 STOPPING 中间态）+ 执行/意图分离

状态：implemented
日期：2026-09-07

## 问题

对照 dsh / Claude Code / deepagents 三家开源实现的子代理生命周期研究（`Interview/highlights/Subagent/01-研究报告/`）暴露两个语义缺陷：

1. **STOPPING 中间态装饰慢操作**。子代理停止的收口路径同步做全量投影回收（跨 loop DB 往返，大投影秒级），于是引入 STOPPING 表达这个窗口，前端配套防抖逻辑（停止期间禁发消息、防重复停止）。而主 Agent 的停止（`run_service.py:778`）是毫秒级乐观终态：内存取消 + 直接落 `INTERRUPTED`（沿用当前快照，未完成工具标记 unknown），界面同步停止——**同一仓库两套停止哲学，慢的那套不是必然**。
2. **停止时清空 followup 队列，已受理消息静默丢失**。`cancel()` 原实现 `entry.followups.clear()`——`send_message` 已返回成功的补充指令，一按停止全部消失且无反馈。三家对照对象都不这么做：dsh `cancel(cause, {keepInbox: true})`（中断当前轮、保留收件箱）、Claude Code 杀后台子仍带 `extractPartialResult`、deepagents 用 `interrupt` 策略注入。

## 决策

三个互相咬合的决定：

1. **停止 = 乐观终态，对齐主 Agent**。`cancel()` 对 RUNNING 任务受理即落 `CANCELLED`（快照立即对前端生效，状态机六态简化为五态，STOPPING 删除）；协程取消 fire-and-forget；部分成果回收与终态通知由**执行协程自身的收口路径**完成——静止边界正常到达时带完整 outcome 回收，宽限超时（默认 30s）走硬杀的 CancelledError 路径（outcome=None，进度摘要回收），`_force_terminal` 对账兜底不依赖协程配合。并发槽随之在受理时刻释放（`_SLOT_STATUSES` 删 STOPPING）。
2. **执行/意图分离：CANCELLED 可冷恢复续聊**。新增 `_RESUMABLE_TERMINALS = {COMPLETED, CANCELLED}`——停止只终止执行，排队与后续的 followup 意图保留；终态后 `send_message` 同 thread 开新 turn（复用 COMPLETED 冷恢复机制），受理时清除停止信号与宽限定时器。FAILED/TIMED_OUT 仍拒绝。
3. **执行侧协作退出改信号驱动**。`_TaskEntry.cooperative_stop_signalled`（线程同步置位）替代状态检查驱动静止边界退出（模型消息完整/工具结果落定两处）与停止期间 HITL 拦截；超时入口 `_on_task_timeout` 同款乐观终态（受理即 TIMED_OUT）。`_try_transition` 的守卫从「STOPPING 不得被覆写」改为「终态不得被覆写」——乐观终态下执行侧的恢复/审批/followup 写入不得复活已停任务。

通知时序的代价与兜底：终态事件与通知现在**晚于**状态（等执行侧收口携带部分成果），`terminal_published` 归属权保证恰好一次；前端删除全部 stopping 交互（禁发 toast、防重复停止、StopSendButton 的 stopping prop、任务面板/类型定义中的 stopping 分支），终态后发送即冷恢复。

## 备选方案

- **保留 STOPPING、仅异步化投影回收**：治标——中间态仍存在，前端防抖逻辑仍需维护，状态机不减负。
- **cancel 自起后台收口协程**（`_schedule_stop_finalize`）：实施过一版，被否——与执行协程自身的收口竞争 outcome（后台协程拿不到静止边界的完整投影，部分成果回收降级为空），且两个收口路径靠归属权去重属于无谓复杂。终态事件天然属于「知道最多上下文的那一方」（执行协程），cancel 只负责受理与兜底武装。
- **纯推导重构（dsh 路线，三态从事实推导）**：否决——AWAITING_APPROVAL（子代理 HITL 是产品能力，dsh 锁死审批 never 是消除场景）与乐观终态后的 API 契约仍需显式枚举；dsh 的极简以砍掉「停止中反馈」与「子代理审批流」两个产品能力为代价，Noesis 保留这两个能力。
- **CANCELLED 不可续聊（保持原语义，仅消灭静默）**：否决——执行/意图分离是三家对照的共识方向；冷恢复机制（COMPLETED 路径）已存在，扩展一个枚举值的成本远小于维持「停止即丢意图」的心智负担。

## 代价

- 终态后 `task.result` 有一个「后台回收中」的空窗口（乐观受理与投影回收完成之间）；消费方（`check_task` 文案）已标注「部分产出在后台回收中，稍后可查收」。
- 通知晚于终态（秒级窗口）；换来的是通知必含部分成果且恰好一次。
- 主 Agent run 状态机的 STOPPING（`chat/runs/models.py`）与本决策无涉，保留原样——两套语义刻意不同：主 run 的停止面向 SSE 流收尾，子代理停止面向任务表。

## 实施后 review 修复（两轴 review 发现，均已修）

初版实施经 standards/spec 双轴 review 发现四个并发缺陷与一处 spec 漂移，修复后 104 测试全绿：

1. **CancelledError 收口守卫死亡**：`_arun` 的硬杀兜底分支检查 `not task.status.is_terminal`——乐观终态下该条件恒 False，硬杀路径的部分成果回收与通知延迟到对账 60s 且丢回收。改为 `not terminal_published and (cooperative_stop_signalled or not is_terminal)`。
2. **冷恢复未中和旧协程**：cancel 后旧协程仍在等静止边界，冷恢复清信号后旧协程复活跑完——与新 `_arun_followup` 双流竞争共享 run/result。冷恢复时取消 `entry.future`。
3. **在飞对账 task 杀复活任务**：`_disarm_terminal_timers` 只取消定时器不取消已起的 `_force_terminal` 协程，迟到的强制终态会终态化复活后的 RUNNING 任务。冷恢复时取消 `stop_reconcile_task`。
4. **`terminal_published` 冷恢复不重置**：复活轮永不发终态事件与通知（COMPLETED 冷恢复的既有缺陷，CANCELLED 续聊成为一等路径后必须修）。冷恢复时重置。
5. **spec 漂移**：`agent-background-tasks/spec.md` 仍 SHALL 着 STOPPING 中间态（状态清单、并发槽、stop API 覆写、四个 Scenario）——按新语义整体重写。

另清理：`_finalize_task` 返回值死分支 ×2、调度窗口分支改为直接停止收口（原 return 会把终态事件延迟到对账）、过时注释与测试名、`cancel_task` 文案区分协作/即时路径。
