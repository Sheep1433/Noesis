# 决策：run 终态读路径与重试瞬态的语义边界

状态：implemented
日期：2026-09-03

## 问题

LLM 重试中间件在网关 429/瞬时错误时发 `run-status(retrying, attempt_id=N)` 帧。这帧进了 run 状态机后产生两条独立缺陷：

1. **终态读路径陈旧**：终态事件（RunCompleted/RunError）按 pending_terminal 流程只应用在 projection 的 clone 上，`handle.state` 在 commit 时换绑，但 `handle.snapshot_provider` 仍指向原始 projection。原始 projection 被 retrying 钉死（重试恢复后无帧置回 running），导致 commit 后 `GET /runs/{id}` 在整个 300s 终态保留窗口内返回 `retrying` + `finish_reason=None`（finish_reason 在 clone 上）。测试轮六个 run 中三个「DB 已终态但 GET 永远非终态」、三个 error run 的等待器同样看不到 error 终态，均此因。
2. **健康 run 被误杀**：重试帧 payload 的 `attempt_id` 是单次模型调用的重试位次，被 projection 当成 run 级 attempt 全局抬升；并行/在途调用按起点戳记的旧 attempt 帧随后被 `apply_event` 严格一致校验判为 `StaleAttemptEvent` 致命异常，杀死 producer，run 以 RUN_FAILED 收尾（日志实证 82f2045c/eaf1224f/1b09d638）。

## 决策

- **`retrying` 不进入 run 生命周期状态**。它是单次模型调用的瞬态，帧照常 fan-out（前端重试提示不受影响），projection 不写入 `self.status`。run status 词表收敛为 `queued | running | hitl_pending | completed | partial | error | interrupted`。
- **`attempt_id` 不进入 run 级 attempt**。帧内值是遥测字段（`model_calls.attempt` 的重试位次，bridge 按模型调用起点戳记），producer 一律以 run attempt（`projection.attempt_id`）发布事件；run attempt 只由 run 生命周期（HITL resume、冷恢复行）定义，当前恒为初始值。
- **终态 commit 换绑 `snapshot_provider`**。`_commit_terminal_candidate` committed 分支在换 `handle.state` 的同时把 provider 换绑到终态 projection——handle 的状态读路径（`RunService.get`、`subscribe`）在任何时刻都不该与 `handle.state` 分叉。
- **同类根因的第三个修复**：`read_file_bound.py` 移除 `from __future__ import annotations`——langchain `StructuredTool._injected_args_keys` 只认 `signature()` 的原始注解对象，字符串化注解会让注入键探测为空、`_parse_input` 剥掉 ToolNode 注入的 runtime。

## 备选方案

- **重试恢复时补发 `run-status(running)` 帧**（中间件 emit resolved 事件）：被否——只修读路径不修状态写入，终态读路径缺陷仍在（任何非 RUNNING 瞬态都会钉死原始 projection）；且并行模型调用下 running/retrying 来回翻转，状态信号噪声大于价值。
- **删掉中间件 payload 的 `attempt_id` 字段**：被否——bridge 的 `_current_attempt_id` → `_model_attempt_ids` → `model_calls.attempt` 遥测链消费它标记每次调用的重试位次（契约测试 `test_model_attempt_ordinal_is_per_call` 钉住），删字段等于砍掉既有的逐步模型调用遥测能力。
- **`apply_event` 把 attempt 不匹配从 raise 降级为 drop**：被否——raise 是 run attempt 一致性的硬不变量守卫，保留它可以把「帧位次混入 run attempt」这类接线错误在第一时间炸出来；正确修法是让位次根本不进入该校验（producer 侧），而不是放宽校验。
- **`RunProjection.snapshot()` 放弃 `self.status != RUNNING` 时信任 projection 的回退逻辑**：被否——该回退承载 HITL_PENDING 等真实生命周期状态的快照语义，一刀切砍掉会破坏 HITL 读路径；provider 换绑才是对「终态读什么」的精确回答。

## 后果与代价

- run status 不再出现 `retrying` 值：session 信令与 GET 快照在重试期间报 `running`。会话列表不再展示「重试中」，代价可接受（此前展示后会被钉死到终态，更糟）；前端重试横幅消费的是 wire 帧，不受影响。
- 旧的迟到帧拒绝机制（WireFrame.attempt_id 戳与 handle attempt 比对）实际失效：run attempt 恒定后两者永不失配。机制保留但惰性——若未来引入真正的 run 级 attempt 轮转（如 HITL resume 产生新 attempt），需重新设计帧位次与 run attempt 的隔离。
- `docs/engineering/platform/chat-streaming.md` §5 的 run status 词表同步收敛；回归测试 `tests/test_run_retry_terminal_read.py` 五条钉住全部不变量（瞬态不入状态、位次不抬 attempt、终态换绑、订阅者终态可达、迟到帧不杀 producer）。
