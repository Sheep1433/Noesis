# 决策：共享数据目录多实例写安全——日志按写者切文件与原子写收编

状态：implemented
日期：2026-11-04

## 问题

`.noesis/` 被 web / control / worker 三角色（及 compose `--scale` 出的多副本）bind 同源共享，两类实际故障：

1. **日志写冲突（生产已发生）**：`logging.py` 文件名只有日期（`{日期}_noesis.log`），多进程写同一文件；loguru 的 50MB 轮转与 zip 压缩是进程内行为，互相覆盖——生产 logs 目录同一天出现两个进程各自轮转出的 zip。`--scale worker=N` 会放大为 N+3 个进程写一个文件。
2. **非原子直写**：附件上传、知识库解析缓存等七处直写目标路径（`write_text`/`write_bytes`），共享目录上读方（worker 沙箱、缓存加载）可能拿到半截内容；`memory/store.py` 已有一份 `_atomic_write`，但临时名无并发区分，且未推广。

## 决策

1. **日志文件名加「角色_实例」段**：`{日期}_{角色}_{实例}_noesis.log`。角色取**入口脚本名**（`Path(sys.argv[0]).stem`，容器里跑的就是 `python web.py`，三种启动形态通吃，compose 零改动）；实例取**主机名**（compose 副本主机名即容器 ID，天然唯一；本地为主机名）。
2. **原子写收编到 `noesis/fsutil.py`**：`atomic_write_bytes` / `atomic_write_text`，同目录临时文件 + `os.replace`，临时名带 uuid（跨进程与同进程多线程都不互踩）。七处写入统一迁移：附件上传、解析 markdown、parse_cache、kb 暂存、用户通道配置、用户 MCP 默认配置，并收编 `memory/store.py` 的私有 `_atomic_write` 删除原实现。

## 备选方案

- **`NOESIS_ROLE` 环境变量标识角色**：被否（曾随首版实现引入后删除）——compose 需为三个服务各加一行才能生效，而 argv stem 零配置达到同一效果；仓库无工厂式启动形态，属无消费者的配置键。
- **纯 pid 或 uuid 做实例段**：被否——pid 随重启变化，日志检索要跨天拼多文件；容器主机名（=容器 ID）在副本生命周期内稳定。
- **memory/store.py 式固定临时名（`.{name}.tmp`）**：被否——同进程多线程（`asyncio.to_thread` 调用链）会互踩临时文件。
- **日志改 per-role 子目录**：被否——目录层级变化影响运维查看习惯，文件名前缀已足够区分，且保留按天平铺的现有布局。

## 代价

- 本地单进程日志文件名变长（`{日期}_app_{主机名}_noesis.log`），旧文件成为孤儿但不破坏（全仓无按文件名模式的采集/retention 依赖，已核）。
- 原子写在写入路径上多一次 rename，微秒级，无感。
- 跨机共享 `.noesis`（NFS 等）仍然不被本决策支持——fsync 语义与沙箱路径一致性约束未变，跨机扩容需另立决策（状态分层、共享面走对象存储）。
