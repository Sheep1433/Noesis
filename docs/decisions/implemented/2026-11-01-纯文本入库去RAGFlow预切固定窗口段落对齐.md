# 决策：纯文本入库去 RAGFlow 预切，固定窗口段落对齐

状态：implemented
日期：2026-11-01

## 问题

纯文本（`.txt`/`.csv`）入库走 `deepdoc_service._parse_txt` 的 RAGFlowTxtParser 128 token 预切，再由适配器按 chunk_size 聚合成正式 chunk。三个代价：

1. **切分不可声明**：最终 chunk 边界落在「128 token 倍数附近」，由 RAGFlow 分词器决定——策略说不清、跨 deepdoc 版本可能漂移。RAG 评测扩充计划（erb-e2e 换 1 万篇语料）要求 chunk 口径可声明可复现，此路径直接冲突。
2. **架构绕路**：纯文本没有版式信息，deepdoc 解析无事可做，为此还要做 sys.modules 预加载 hack 绕开 deepdoc 包的重依赖（vision/xgboost）。
3. **评测与生产口径分叉**：评测直写导入与生产 deepdoc 路径产出不同 chunk 边界，报告要额外解释一层差异。

预切的来源是 RAGFlow naive 模板默认值（128），不是本仓库的设计决策；Noesis 的「deepdoc blocks → 适配器聚合」架构对有版式文件是正确的，txt 只是架构的搭便车者。

## 决策

1. **`_parse_txt` 整篇单块**：`.txt` 解析直接返回一个 block（整篇文本）。短文（≤ chunk_size）自然成为单 chunk；超长走适配器既有的「超长单块 → 固定窗口」路径。RAGFlowTxtParser 调用与 import hack 删除。
2. **`_fixed_window_chunks` 段落对齐**：窗口尾部 25% 区间内优先在段落边界（`\n\n`）断开，找不到退换行，再退硬切。字符窗口不依赖任何分词器，规则一句话可声明（`fixed window, paragraph-aligned`）。三个调用方（超长块、表格、markdown 回退滑窗）共享；无段落分隔的文本（表格）行为与纯硬切一致。
3. 评测导入与生产入库从此同一条切分代码路径，chunk 口径差异消除。

窗口参数不变（集合级 chunk_size/chunk_overlap 配置面不动）；官方向量基线 512 token ≈ 2000 英文字符，与生产默认量级一致，扩充评测可直接与官方基线同表对照。

## 备选方案

- **保留预切、评测侧单开直写路径**：被否——评测与生产分叉的解释成本正是要消除的对象；且 128 token 边界的 chunk 对 BM25 短语有轻微截断伤害。
- **整篇永远单 chunk（不切超长文档）**：被否——超过 embedding 上下文的文档必须切；固定窗口是超长的兜底。
- **语义切分 / 父子切片**：被否（对本次改动而言）——ERB 语料平均约 1000 token，2000 窗口下多为 1-2 块，语义切分收益上限接近零且引入 embedding 版本依赖；父子切片是产品功能（引用定位粒度），属另一条线。

## 代价

- 已入库集合的旧 chunk 边界与新路径不同——**不自动重切**（Qdrant payload 的 effective_processing_params 快照仍标记 deepdoc 版本；需要重切时按「处理参数变化后应重新解析和入库」既有约定显式重建集合）。erb-eval 扩充计划本来就是新建 erb-eval-10k 全量入库，不受影响。
- 段长超过窗口四分之一的文本会按声明规则退硬切（段中截断），overlap 兜底——ERB 英文语料段落 200-400 字符 vs 2000 窗口，几乎不触发。
- `.csv` 同走该路径（此前也在 `_TEXT_EXTENSIONS` 内）：csv 若含多行文本，段落对齐可能在行边界断开——与旧的 128 token 预切相比无行为劣化。
- 编码兜底改为「UTF-8 失败退 GBK」（原 RAGFlow 的 get_text 自带编码探测）：GBK 中文 txt 不再静默乱码；其余编码不兜底、直接抛错。

## 验证

`tests/test_kb_deepdoc.py` 新增三条红→绿测试：`_parse_txt` 整篇单块；`_fixed_window_chunks` 段落对齐 + 游标覆盖无缺口；txt 入库端到端（短文单 chunk、超长窗口切分、片段均为完整段落后缀、段落零丢失）。既有回归面：KB/chunk/deepdoc 相关 131 passed、retrieval/eval 相关 178 passed、api_contract 25 passed。
