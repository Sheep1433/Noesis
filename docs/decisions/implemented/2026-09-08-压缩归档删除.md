# 决策：删除消息压缩的会话原文归档

状态：implemented
日期：2026-09-08

## 问题

压缩中间件每次压缩都把被压缩掉的原文整篇写入 Agent 沙箱的
`/workspace/conversation_history/{thread_id}/{digest}.md`（压扁、无索引的快照副本）。
session-history-search 落地时把它定性为「审计/调试用途，检索不消费」而保留现状。
压缩评测切到真 Agent 路径后实测暴露其真实危害：**闭卷组的模型用 grep 工作区直接
搜到归档文件里的原文，答对了本应只能靠 search_history 检回的细节题**——归档构成
一条绕过检索设计的「会话全文后门」，对任何有文件工具的 Agent 开放（还可能把失控
量级的 token 经 grep 灌回上下文）。同时它是零消费方的第三份冗余副本：权威原文在
`t_chat_message`（压缩只改 checkpoint，库内原文不动），运行时没有任何代码读
`archive_path`。

## 决策

删除归档机制：`CompactionMiddleware._archive` 方法、`archive_required` 与 `backend`
构造参数（backend 仅归档使用）、`CompactionResult.archive_path` 字段、压缩策略状态
里的 `last_archive_path` / `event.archive_path`，以及 `compaction_service` 中仅为归档
服务的 `_archive_backend` 沙箱装配（`/compact` 宿主路径随之不再拉起沙箱）。
被压缩原文的唯一权威源是 `t_chat_message`，取回路径是 `search_history`。

## 备选方案

- **归档挪到 Agent 不可见的存储（保留审计副本）**：否——零消费方的东西留一份就多
  一份漂移风险；审计需求 DB 已覆盖（带序号、归属、时间）。
- **生产保留、评测侧清沙箱规避**：否——治标，线上旁路仍在，且评测与线上形态
  被迫分叉。
- **给归档文件建索引作为检索源**：session-history-search 设计时已否（冗余存储 +
  与库内状态可能漂移），本次实测进一步证明归档不该存在。

## 代价

- 压缩后沙箱不再有原文副本（原本也无运行时消费方）。
- 历史 checkpoint 策略状态里残留的 `archive_path` 字段无人读取，无需迁移。
- 历史会话沙箱里已写入的归档文件不主动清理（随会话工作区生命周期管理）。

## 验证

- `uv run pytest tests/ -q`（排除 api 目录）1566 passed；`tests/api_contract` 21 passed。
- 删除 `test_archive_failure_prevents_compaction_publication`（机制不存在），
  `/compact` 宿主路径测试同步（不再装配 backend）。
