# 决策：工具上下文投影 append-only 化与预算收敛

状态：implemented
日期：2026-09-02

## 问题

上下文投影层存在两个改写已发送历史的机制，直接拉低 prompt 缓存命中率；工具输出上限链路自相矛盾形成卸载追逐循环。实测证据：

- 预算中间件的参数卸载滑动窗口（最近 12 条保留原文）每步前移一格、每步改写一条已发送消息——一轮 18 步子 Agent run 中 step 16→17 输入不增反降 5,355 token，多步综合缓存命中率 67.7%（同形状 append-only 历史的结构值为 91.8%，缺口即每步分叉的累计代价）。
- read_file 无源头上限：Noesis 为让预算中间件单点拥有替换语义，把上游「截断 + 驱逐」共用的参数置 None，连带失去截断——500 行读取约 30k 字符必超 24k 预算被卸载，模型读 artifact 又超限再卸载（近 7 天 read_file 超限 40 次，最大 10 条全是读 artifact 的输出）。
- 批次合计 48k 预算替换「每条都没超单条预算」的中间大小结果，主要受害者是并行检索批次；总量护栏本是压缩层职责。
- Runtime Context 每轮插在最后一条用户消息前且不进历史，位置与内容双变，上一轮全部新增在新一轮再 miss 一遍。

## 决策

以「**同一历史投影两次逐字段一致，发送后永不改写**」为硬不变量重构投影层：

1. **参数卸载入口即定型**：删除滑动窗口，大参数在第一次进入有效历史时替换、之后按内容 hash 重放；投影幂等由替换文本前缀哨兵保证（已替换文本不被当作新的超限输入二次替换）。
2. **删除批次合计层**：只保留单条 24k 预算（`runtime.tool_output_max_chars`）。
3. **read_file 源头封顶**：新增 `runtime.read_file_max_chars`（默认 20,000 ≈ 单条预算 85%），stack 装配层独立包装 read_file 工具（不重启上游驱逐）；新鲜读取永不触发事后替换。
4. **Runtime Context 冻结块**：日期粒度头部块会话首轮冻结（private state 持久化、messages[0] 投影、逐字节不变）；跨日与附件变化走尾部追加声明；中途注入路径（`insert_late_context`）退役。
5. **替换梗概比例化**：600 字符 → 头 2000 + 尾 1000。
6. **web_fetch 单份正文与头尾截断**：删除顶层 `content` 双份存储；`fetch_max_chars` 4096 → 16000；超限页从头部硬截断改为头 75% + 尾 25%（行边界对齐）+ 全文落盘（`/web_pages/`，2MB 上限）+ 页脚精确续读 offset——与 read_file 源头封顶的「行号续读」语义衔接成完整链路。

变更详情见 [openspec/changes/tool-context-append-only](../../../openspec/changes/tool-context-append-only/proposal.md)。

## 备选方案

- **压力触发式批量清理**（上下文占用超阈值时一次性清理旧结果与参数，参照主流 Agent CLI 的微压缩形态）：否决。需要引入阈值状态机；触发瞬间仍是一次全量前缀作废；其「保鲜区」收益（近期大参数保留原文）在实测中无功能必要性——24k+ 参数是整份文件内容类一次性数据。外部参照的实测设计调研（含逐日翻转尾部纠正、冻结头部块的量化代价 ~920K tokens/次改写）存于会话调研记录。
- **保留滑动窗口、改为不滑动的白名单豁免**：否决。任何「先保留、后替换」的两段式都必然在某个时刻改写已发送内容；只有入口定型满足不变量。
- **调小上游 `tool_token_limit_before_evict` 实现 read_file 截断**：否决。该参数同时控制结果驱逐，调小会在 20k 处重启上游卸载，与预算中间件形成双份替换且上游不保留 status/errorCategory/outcome。
- **每条用户消息携带日期戳（替代冻结块）**：否决。语义等价且 append-only，但每轮多一行重复信息；冻结块 + 尾部纠正在同日常态下零额外注入。

5. **工具失败通道单源化**（同日追加）：`ToolFailure` 双文案（message_for_llm/message_for_user）+ Suggestion 行 + `[tool_error]` header + 前端分类文案表四件全部删除，改为**单份短文案**（≤600 字符）：模型 / 入库 / 用户展开态逐字一致（`Error: <短文案>`），前端折叠行通用「执行失败」；pydantic ValidationError 走结构化提取（`file_path: Field required（传入字段：…）`），不再灌 str(exc) 全文；可重试类（网络/超时/基础设施）统一后缀「，可稍后重试」、不可重试不带——重试语义由文案承载，不设显式布尔；errorCategory/retryable 降级为纯 metadata（DB 统计、SUBAGENT_FAILED 判定、预算中间件保语义）。LLM 上游服务商失败（429/503/451）不在本通道，由 `LLMErrorHandlingMiddleware` 承载（退避/上限/熔断/不可重试直达降级），重试决策者是代码不是模型。

## 后果与代价

- 升级后首个请求对既有会话的大参数做一次性入口定型（一次性缓存重置）；替换记录兼容（hash 键控重放机制未变）。
- 失去「保鲜区」：模型刚写入的大文件参数当轮即被占位符替换，需要回看时读 artifact——实测该类参数为一次性数据，功能影响可忽略。
- 多轮缓存率的结构上限由会话形状决定（N 轮均匀增长 ≈ (N−1)/(N+1)，10 轮约 82%），本决策消除的是每轮分叉与每步出血，不是结构本身；网关侧路由换模型与缓存 TTL 仍是环境天花板。
- read_file 封顶后单次读取信息量下降（20k 字符），代价由模型自行用 offset 分段续读承担——比卸载追逐循环（每段读取多一轮工具调用 + 再卸载）便宜。
