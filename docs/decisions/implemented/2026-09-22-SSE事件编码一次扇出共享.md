# 决策：SSE 事件编码一次、扇出共享（encode-once fanout bytes）

状态：implemented
日期：2026-09-22

## 问题

同一条 durable 事件对**每个订阅连接**各执行一次 `encode_run_event → json.dumps → format_sse`（消费循环内）。载荷对所有订阅者完全相同（`run_id`/`sequence`/`attempt_id` 一致，无 per-连接差异），编码 N 次产出 N 份相同字符串——订阅数 × 事件频率的 CPU 纯放大（容量画像 100 并发 run × 2-3 订阅 × 每秒 10-30 事件，高峰档约 9,000 次/秒冗余序列化）。且同一事件存在三种表示：订阅队列里是事件对象、SSE 连接产出字符串、Redis hub 派生 wire dict——编码逻辑分散在两个消费侧。

## 决策

### 1. 编码上移到发布点，envelope 携带 bytes 产物

`_assign_and_buffer`（handle.lock 临界区内、`delivery.commit` 之前）构造 envelope 时调用 `encode_sequenced_event` 一次，`SequencedRunEvent` 新增 `encoded: tuple[bytes, ...]` 字段。**编码必须发生在 commit 之前**——commit 后再回填等于对 frozen dataclass 重建实例，重放缓存与扇出会持有两个不同实例，破坏"缓冲与订阅者看到同一对象"的隐式契约。落库检查点消费方继续读 `event` 字段，不经编码产物。

被否：commit 后 replace 回填 + 二次 append（会重复入缓存、同序号两份）；消费侧 memoize 缓存（事件可变、连接集合动态，失效管理复杂度高于上移）；envelope 惰性字段首次消费时编码（锁内数据结构出现可变缓存，破坏不可变纪律）。

### 2. 双产物单次计算：`(event_name, payload_dict)` 对 + bytes

`encode_run_event` 从"产出 SSE 字符串"改为"产出 `(event_name, payload_dict)` 对"；`format_sse_bytes` 由 payload 一次成帧，`sequenced_event_payloads`（bus/hub wire dict 源）复用同一对列表注入序号——消除"编码字符串再 parse 回 dict"的往返，同一事件从三次序列化降为一次。StreamDone 用 `("__done__", {})` 哨兵对表达（仅 `encode_sequenced_event` 消费为 `[DONE]` 字节）。

### 3. 快照首帧不进共享编码路径

`run-snapshot` 载荷含订阅时刻的 `after_sequence` 与快照状态——per-连接内容，共享即错误。判据：**共享编码只覆盖"载荷对所有订阅者逐位相同"的事件**；durable 事件（序号注入后全连接一致）满足，快照帧不满足。快照与 replay 之外的连接侧帧保留 `format_sse`（str）路径，StreamingResponse 接受 str/bytes 混合生成器。

### 4. 字节计量从估算改精确

`estimated_bytes` 在 `encoded` 存在时按帧字节精确求和（+64 帧头开销），替代 json.dumps 估算。已知行为变化：原先被低估的大事件更早触发慢订阅者隔离——方向正确（原先可能放行超限事件），容量回归需验证隔离路径（待环境，见 tasks 4.3）。

### 5. 边界与豁免

- 锁内编码为纯函数（json.dumps + 拼装），微秒级，不违反"锁内无 I/O"不变式；容量回归若显示临界区劣化，可移至锁外紧邻扇出（序号在锁内分配，先后序天然满足）。
- 主链路 RunManager 无 transient 旁路（主 run 增量是 durable 全流程；`publish_transient` 仅子代理执行器使用），本变更不动子代理侧（jobs/events.py 同模式改造列为后续项，避免一次动两个 DeliveryCore 持有方）。
- 消费侧保留 `item.encoded or encode_sequenced_event(item)` 兜底分支：测试手工构造的 envelope 不带 encoded，且该分支保证旧形态信封的兼容读取。

## 验证

单测 1649 全绿（含双产物往返、多订阅者 `is` 同一 bytes、缓冲单实例无重复、大事件早隔离）；契约门禁 `tests/api_contract` 25/25；事件词表契约测试零改动（词表提取自桥接层类型，与编码层解耦）。待环境项：容量脚本前后对比（tasks 4.3）、Redis 双进程手动验收（tasks 4.4）。

## 备选方案

- **commit 后 replace 回填 + 二次 append**：被否——重复入重放缓存（同序号两份），且缓冲与扇出持有不同实例，破坏"同一对象"隐式契约。
- **消费侧 memoize 缓存**（连接间共享编码结果）：被否——事件对象可变、连接集合动态，缓存失效与生命周期管理复杂度高于把编码挪到发布点；hub 路径仍需第二种表示。
- **envelope 惰性字段（首次消费时编码并回填）**：被否——锁内数据结构出现可变缓存字段，破坏 envelope 不可变纪律；首个消费者承担编码成本，扇出时刻不确定。
- **事件对象直接序列化进 Redis、hub 消费侧解码再编码**：被否——为省进程内 CPU 付跨进程序列化协议层 + 双重编码，负收益。
- **`yield from` 转发**：async 生成器不支持（Python 语法限制），消费循环用 `for frame in ...: yield frame` 表达。

## 影响

改动集中三处：`noesis/chat/delivery/sse.py`（编码入口收敛为双产物）、`noesis/chat/runs/manager.py`（构造点编码 + 精确计量）、`server/api/chat_api.py`（消费循环退化为转发）+ `noesis-cli` 适配（单订阅者 decode 输出）。收益：订阅扇出编码 CPU 从 O(订阅数 × 事件数) 降为 O(事件数)；同一事件三种表示收敛为单次计算双产物。
