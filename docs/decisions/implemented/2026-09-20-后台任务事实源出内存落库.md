# 决策：后台任务事实源出内存落库（bg-task-durable-facts 落地）

状态：implemented
日期：2026-09-20

## 问题

后台任务台把任务目录（`_TASKS`）、排队序（`_PENDING_QUEUES`）、追加消息待执行队列（deque）全部放在进程内存当事实源：终态条目永不回收（内存随任务数线性增长）、工具路径追加的消息重启即蒸发、查询无 DB 兜底（回收/跨进程即「任务不存在」）、shell 任务零落库。openspec `bg-task-durable-facts` 承载改造，审计来源 `docs/bug/background-executor-memory-state-audit.md`。

## 决策

### 1. 三层承载：PG 事实 + 既有 Redis 通道 + 内存执行热集，不建 Redis 队列与租约

`enable-distributed-sse-pubsub` 落地后执行面收敛为单 leader（advisory lock + 任期 fencing），任务状态只有唯一写者——「内存与 DB 分叉」退化为同写者的持久化延迟。DB 行本身就是队列，跨进程扇出已有信令桥：审计文档档位 1 建议的 Redis list 队列与 `SET NX EX` 租约被否——它们是同一互斥的第二次实现，徒增需要重建的第二事实源。代价：接受单 leader 的后台任务吞吐上限（与主 run 同一约束）。

### 2. 追加消息 write-ahead 复用 pending user message 行，不建独立表

HTTP 路径已有「先写 `extra.pending_run: True` 的 user message 行、launch 事务采纳（清标记盖 run_id）」的完整机制。工具路径 `deliver_message` 并入同一模式而非新建 `t_bg_task_followup`（初稿方案，评审推翻）——独立表会给同一意图造第二条并行载体。关键推论：**DB pending 行是队列事实，内存 deque 只是执行镜像**——可续终态（completed/cancelled）保留 pending 行，冷恢复重建条目时从 DB 重载队列（含随行 turn 参数，顺带修掉排队参数重启蒸发的旧 bug）；不可续终态（failed/timed_out）收口即翻转 dropped。采纳是整覆写 extra，重载消费须在覆写前读参数。

### 3. 终态回收资格三件套 + 落库重试耗尽后允许回收

乐观终态使条目受理即呈终态，而部分成果回收/通知落库异步收尾。回收资格 = 终态事件已发布 + 终态落库成功（有界重试沿用主链路 persistence 超时预算）**或重试耗尽** + 通知已记录；retention（默认 1h，可配）自收口完成起算，上限（默认 200）按终态时间从最旧补收。耗尽条目允许回收但不伪造终态——run 行打 `TERMINAL_PERSIST_EXHAUSTED` 诊断位，DB 投影按落库事实回答并携带标注。

### 4. 冷恢复覆盖已回收任务，投递失败不终态化任务

条目回收后 `deliver_message` 从 child session descriptor（version/type/model，launch 已落）解析 worker 配方重建条目并重载队列——descriptor 的「重启后重建」条款扩展到「回收后」。投递失败是消息级事实：消息行翻转 dropped、任务回退先前终态（冷恢复路径）或保持当前状态（链式路径）；冷恢复窗口内受理的停止终态获胜，不回退。改造了 `settle_followup_prelude_failure` 原本把任务落 FAILED 的语义。

### 5. 模型工具 `update_async_task` 更名 `send_message`，API 更名 `/subagent-messages`

主规格「追加消息」条款本就以 `send_message` 为模型侧工具名，代码向规格靠拢，不保留上游别名。静态引用点 `roles.py` 的 `BG_TASK_TOOL_NAMES`（递归委派防线）同步，并补钉住工具名的断言测试（更名前无该测试，改完不会有测试变红）。部署切换接受两个在途影响：checkpoint 旧名工具调用解绑为工具错误（模型可按新名重试）、旧前端 404（刷新即恢复）。

## 备选方案

- **Redis list 队列 + 任务级租约**（审计档位 1）：单 leader 下无跨 worker 出队竞争，第二事实源与第二次互斥实现无收益；执行外置（远期档位）时随外置方案重设计。
- **独立 write-ahead 表 `t_bg_task_followup`**：与既有 pending 行模式构成双载体（内容双存、两套投递确认、对账扫两张表）。
- **重启后未投递追加消息自动重投**：重启后上下文与时效已变，静默代执行有越权风险；改为 dropped 标记 + `undelivered_messages` 投影计数，是否重新下达回到人/模型的下一次判断。
- **落库失败条目永久留热集**：DB 兜底会永久返回 running，与已送达通知矛盾；不回收又有界内存目标失效。取「有界重试 + 耗尽回收 + 诊断位」。
- **排队序持久化专列**：重建排序用行 `created_at` 已满足跨会话公平，毫秒级提交序复刻是投机精度。
