# 决策：定时任务通知落库与重启对账（无人值守 Phase 2）

状态：implemented
日期：2026-09-19

## 问题

远程服务器生产事故（定时任务会话父 Agent 永久等待）定位出三个系统性缺口，Phase 1 修复了直接根因（continuation 仅 COMPLETED 触发的门控缺陷），本记录解决其中两个：

1. **通知只存内存**：`notifications.py` 的待送达队列是进程内 dict——无人值守会话（定时任务）依赖「终态通知 → 注入下一轮 → check_async_task 收果」这条链，进程重启后未送达通知蒸发，链路断裂；且会话已死的通知永不清理。
2. **scheduled run 重启无对账**：调度器在进程内 `await` 整个 agent 执行（`execute_with_record`），重启即丢失执行体；`claim_due_tasks` 已推进 `next_run_at`（下次触发照常），但遗留的 queued/running 运行记录行无人收口——设置页永久显示 running，任务行 `last_status` 卡死。

## 决策

### 1. 通知持久化：只存未送达的表 + 启动恢复

- 新表 `bg_task_notifications`（id / session_id / payload JSON / created_at）**只存未送达行**：`take_undelivered` 送达后即删行，无 delivered 标记、无历史堆积；30 天仍未送达的行视为会话已死，由恢复入口清理。
- 写入：`record()` 内存追加 + fire-and-forget 落库（经 `run_on_main_loop`，与终态收口落库同款跨 loop 通道）。
- 恢复：leader-only 启动对账块调用 `restore_undelivered_notifications`，按 `created_at` 升序装载回内存注册表（`load_persisted`，按 id 幂等）。
- **送达墓碑**：内存记录本进程已送达的通知 id（每会话上限 512）。删行是异步的，「标记送达 → DB 行消失」之间存在窗口，窗口内任何恢复装载都会重复注入——墓碑让内存对"本进程已送达"保持权威，关闭该窗口。
- 跨 loop 装配：经 `agents.background.ports` 新增 `NotificationStorePort`（实现 `services.bg_notification_store`，组合根 `register_runtime_ports` 注册）。与其他端口不同，**未注册静默降级为纯内存**——`record` 在大量单测中触发，无服务装配时不能抛错。

### 2. scheduled run 重启对账

- `ScheduledTaskService.reconcile_interrupted_runs`：启动时（调度器启动前、leader-only）把遗留 queued/running 收口为 `interrupted`（error_category=server_restart），任务行 `last_status`/`last_error` 同步；终态行不动；幂等。
- `interrupted` 为新终态值：非任务自身失败（failed）也非用户主动取消（cancelled），语义独立；前端 run 状态词表已有「已中断」。interrupted 的运行可重试（后端资格判定与前端按钮同步放开）。

## 备选方案

- **在子会话 run 行上标记未消费（不建表）**：被否。通知是会话级聚合（一次终态一条、多任务合并成块注入），挂在 run 行上需要拼装与去重，且 run 行的写方（收口路径）与读方（注入路径）职责交缠。
- **通知表带 delivered 标记并保留历史**：被否。历史通知无人消费（注入是一次性的），纯堆积；送达即删让表天然有界，孤儿由 30 天清理兜底。
- **恢复时机选「每次 run 组装时按会话查库」**：被否。每个 SuperAgent run 多一次 DB 往返；当前单 leader 架构下启动一次性恢复已覆盖重启场景，多实例部署时再升级为按会话恢复。
- **scheduled run 收口复用 failed**：被否。掩盖「进程重启」与「任务失败」的语义差异，用户会把重启误读为任务本身出错；interrupted 独立成值后重试入口照常开放。

## 代价

- 每条通知一次 insert + 一次 delete（跨 loop fire-and-forget）。落库失败降级为 Phase 2 之前的纯内存行为（通知丢失窗口不变）；删行失败最多导致**重启后**重复注入一次——通知投递从进程内恰好一次变为跨重启 at-least-once。
- 内存送达墓碑每会话最多 512 个 id，超限整会话清空（病态量级下退回 at-least-once）。
- 前端需认识 interrupted 状态（tag 显示与重试按钮；其余状态渲染不变）。
