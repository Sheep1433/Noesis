# 决策记录

一条决策记录回答一个问题：**当时为什么这么定、否了什么、代价是什么**。代码和架构文档描述「现在是什么」；决策记录保存代码装不下的判断依据。它替代了原 `docs/NOTES.md` 的决策卡片职能（2026-09-01 机械迁入，见文末「legacy 说明」）。

## 放置与生命周期

路径编码状态：`{proposed|implemented|rejected}/YYYY-MM-DD-主题.md`，文件名日期为**首次提出**日。

- `proposed/` — 尚未实现的提案，实现它的提交把它改写为 implemented 现在时态并核实路径与机制。
- `implemented/` — 已生效的决策，**随代码同提交保持事实同步**（路径、名称、机制变了就同一提交更新对应事实；判断依据本身不改，被推翻就新开记录）。
- `rejected/` — 被否的提案，状态行必须带一行落选理由。只在「该方案仍是一个诱人的错误」时保留，否则连同删除。

## 何时必须写

非平凡改动（改变行为、架构、跨文件契约、开发流程、测试策略）的**同一提交**必须新增或更新至少一条记录；更新既有记录即满足规则，不重复开档。纯机械或纯局部修改豁免。

openspec 归档接缝：change 归档时把 `design.md` 中有长期价值的判断依据与被否方案提炼为一条 implemented 记录（openspec 归档件是变更期文档，随时间失去约束力；决策记录是长期权威）。

## 文件格式（CI 校验，见 scripts/verify_decision_format.py）

```markdown
# 决策：<标题>

状态：<proposed | implemented | rejected — 一行理由>
日期：YYYY-MM-DD

## 问题
（不依赖方案可独立理解的动机）

## 决策
（定了什么）

## 备选方案          ← implemented 必填
（否了什么、为什么输。没有这一节，同一裁决会被反复重新争论）

## 后果与代价
（接受了什么风险、放弃了什么能力、何时应重新评估）
```

## 取代审计

新记录落档时检查同主题旧记录：

- **完全取代** — 旧记录的独特判断依据并入新记录，旧文件删除，入链修复。
- **部分取代** — 两条记录双向交叉链接，各自事实保持当前。

## legacy 说明

`implemented/` 中带「迁移：自 docs/NOTES.md 机械拆分」标记的 138 条为历史迁入：正文零改写，不满足新格式（多数无备选方案节），**格式校验豁免**。它们的价值密度参差，后续按「是否仍能指导未来改动」逐条判断：保留、归档或并入新记录；在完成一轮整理前整体视为可搜索的历史素材，其中被后续记录取代的以新记录为准。未带决策日期的工程操作记录在 [docs/engineering/legacy-worklog.md](../engineering/legacy-worklog.md)，不属于本体系。
