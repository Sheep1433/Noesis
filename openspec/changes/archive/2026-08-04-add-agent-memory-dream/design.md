## Context

用户消息已按用户、会话持久化，L2 目录和列表/文本搜索也已存在，但没有生产 L2 的流程。`UserMemoryService` 还把 USER.md 中一段标记文本解析成固定表单，增加了两套编辑方式。SuperAgent 只注入 USER.md 与 AGENTS.md，也没有跨会话检索工具。

## Goals / Non-Goals

**Goals:**

- 从指定自然日的已完成消息生成稳定、可读、可检索的 L2 记忆。
- 每条记忆保留来源标识，并能在用户权限范围内读取原始上下文。
- 重复执行结果幂等；L2 不进入默认 prompt。
- 让用户和 SuperAgent 使用同一套检索 Service。
- USER.md 只保留 Markdown 原文编辑。

**Non-Goals:**

- 首版不自动修改 USER.md 或 AGENTS.md。
- 首版不保存 reasoning、工具原始输出、附件正文或未完成消息。
- 首版不引入 embedding、Qdrant collection 或跨用户共享记忆。
- 不把原始聊天历史复制到 L2。

## Decisions

### 1. L2 使用结构化 Markdown 文件

`backend/noesis_server/services/memory_dream_service.py` 负责查询当日消息、生成条目并原子替换 `memory/YYYY-MM-DD.md`。文件包含稳定 entry id、分类、摘要、关键词、来源 session/message id。相比新增数据库表，这与既有用户文件模型一致，用户可直接查看和导出；后续可在不改变文件契约的情况下增加索引。

### 2. 首版采用确定性提取

整理器从 user/assistant 的 text part 提取有内容的问答对，做长度限制、去重和敏感内容过滤，并形成简短摘要。这样测试稳定且不新增模型调用成本。后续 LLM 摘要器可以实现相同接口，但不得改变来源和幂等规则。

### 3. 以自然日和内容摘要保证幂等

API 接收 `date` 与可选时区；Service 按该时区换算 UTC 时间范围。entry id 由用户、来源消息与规范化文本摘要计算。每次运行重建目标日期文件并通过临时文件原子替换，重复运行不会重复追加，失败时保留旧文件。

### 4. 检索与来源读取分开

`search_memory` 只返回精简条目、分数和来源标识；`get_memory_source` 再按当前 user_id 校验会话归属并返回相邻消息。Agent 先搜索再按需追溯，避免长历史进入上下文。两个工具通过闭包绑定 user_id 和数据库会话，不能由模型指定其他用户。

### 5. 定时整理沿用应用内轮询

新增轻量 scheduler 每小时检查各用户本地时区的上一自然日是否已有成功标记；标记写在 L2 文件头。设置页保留手动触发，以便补跑。自动任务失败只记录日志，下次轮询继续重试，不影响聊天服务启动。

### 6. UI 只提供原文画像和记忆操作

`MemoryEditorSection.vue` 删除固定字段 Tab 与对应 API 调用。L2 区域增加日期、整理按钮和结果状态，搜索结果展示分类、摘要及来源入口。产品文案使用“记忆”，避免把 L2 描述为用户日记。

## Risks / Trade-offs

- [确定性摘要可能不够精炼] → 限制首版为事实片段和问答摘要，保留来源；后续替换摘要器。
- [文件数量增长导致全量搜索变慢] → 限制扫描日期范围和结果数；后续增加派生索引，不改变 API。
- [消息包含敏感信息] → 排除 reasoning、tool parts、错误和未完成消息；来源接口继续执行用户权限校验。
- [多进程同时整理] → 使用目标文件原子替换；同日期最后一次完整结果生效。
- [定时器漏跑] → 设置页允许指定日期补跑，自动检查采用“文件成功标记”判断。

## Migration Plan

1. 部署兼容 API 与 Service；现有 L2 文件继续可列出和搜索。
2. 前端移除结构化画像入口并增加整理入口。
3. 启动 scheduler；仅处理部署后的上一自然日，不批量补写历史。
4. 回滚时停止 scheduler 并移除新 API/tools；生成的 Markdown 文件可以保留，不影响旧版本。

## Open Questions

- 后续是否用模型摘要替换确定性摘要，由真实数据质量评估决定。
- 当文件检索达到性能阈值后，再决定 SQLite FTS 或向量索引。
